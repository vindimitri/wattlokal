Wattlokal – Verbesserungen (Senior-Review)
Aktualisiert: Juli 2026 – Live-MVP inkl. Domain, Resend, Turnstile, Admin, Cleanup, Landing

Wenn ein Senior Web Developer und ein Senior Security Engineer die aktuelle
Infrastruktur bewerten, ergibt sich folgendes Bild.


================================================================================
GESAMTURTEIL
================================================================================

Architektur für eine lokale Machbarkeitsstudie?   Ja – solide
Overengineered?                                   Nein
Enterprise- / Banken-Standard?                    Nein
Für Nachbarn-Kampagne nutzbar?                    Ja – mit Klartext-Restarbeiten

Kern ist richtig: Double-Opt-in, gehashte Tokens, kein Browser→DB, Captcha,
Pending-Cleanup. Was fehlt, ist Härten und Betrieb – kein kompletter Neubau.

Ein-Satz: Nicht neu schreiben – Recht finalisieren, fail-closed, dann Auth /
Rate-Limit / Audit nachziehen.


================================================================================
ARCHITEKTUR (IST-STAND)
================================================================================

UI:     /  /anmelden  /bestaetigen  /danke  /datenschutz  /impressum  /admin
API:    POST /api/register
        GET  /api/cron/cleanup-pending
        POST|DELETE /api/admin/login
        GET  /api/admin/export
Daten:  Supabase registrations (pending → confirmed)
Mail:   Resend (@wattlokal.de)
Abuse:  Cloudflare Turnstile + In-Memory Rate Limit
Auth:   ADMIN_SECRET → HttpOnly-Cookie
Host:   Vercel + Domain IONOS/Vercel DNS

Flow: Formular → Validierung + Captcha + Rate Limit → pending + Token-Hash
      → Bestätigungsmail → /bestaetigen → confirmed → Admin/CSV

SENIOR WEB DEVELOPER
================================================================================

Was gut ist
-----------
[x] Klarer Scope: Landing → Formular → Double-Opt-in → DB
[x] Saubere Trennung (validation, tokens, email, Routes)
[x] Double-Opt-in mit gehashtem Token + TTL
[x] Serverseitige Validierung
[x] Pending-Cleanup (Cron: Token abgelaufen oder älter als 7 Tage)
[x] Admin force-dynamic, noindex; CSV no-store
[x] Resend + Domain, Captcha, Design, Landing-Karussell
[x] Impressum + Datenschutz-Struktur vorhanden

Was er kritisieren würde
------------------------
[ ] Rate Limit nur In-Memory → auf Vercel über Instanzen wirkungslos
    Datei: lib/rate-limit.ts
    → Upstash Redis / Vercel KV

[ ] Captcha fail-open: fehlt TURNSTILE_SECRET_KEY → Captcha wird übersprungen
    Datei: lib/turnstile.ts
    → In Production hart ablehnen (fail-closed)

[ ] Mail ohne RESEND_API_KEY: Link nur in Logs (lokal ok, Prod gefährlich)
    Datei: lib/email.ts
    → In Production ohne Key Register verweigern

[ ] Confirm per GET mit Seiteneffekt (Scanner/Bots können bestätigen)
    Datei: app/bestaetigen/page.tsx
    → Confirm per POST / One-Time-Form

[ ] Race bei parallelem Erst-Insert gleicher E-Mail (kein robustes Upsert)
    Datei: app/api/register/route.ts
    → onConflict / Idempotenz

[ ] Confirmed-Daten: Speicherdauer in Datenschutz genannt, technisch nicht
    enforced (Cron löscht nur pending)
    → Retention-Job für confirmed (löschen/anonymisieren)

[ ] Keine automatisierten Tests, keine Alerts bei Mail/DB-Fails
[ ] Rechtstexte noch Platzhalter (Impressum/Datenschutz)
[ ] Dead Code: authorizeAdminRequest ungenutzt (lib/admin.ts)
[ ] Admin = Shared-Secret – Studie ok, kein Produkt-Standard

Priorität Web
-------------
[x] Production fail-closed (Turnstile + Resend + nötige Env Pflicht)
    → lib/env.ts, lib/turnstile.ts, lib/email.ts, /api/register
[x] Admin-Login Rate Limit (5 Versuche / 15 Min. pro IP)
    → /api/admin/login
[x] Security-Headers + CSP (next.config.ts)
[x] Register Anti-Enumeration (confirmed → gleicher Success-Response)
[ ] Rate Limit Formular härten (Upstash Redis) – aktuell In-Memory
[ ] Confirm per POST statt GET
[ ] Confirmed-Retention passend zur Datenschutzerklärung
[ ] Rechtstexte Platzhalter ersetzen


================================================================================
SENIOR SECURITY ENGINEER
================================================================================

Was gut ist
-----------
[x] Service Role nur serverseitig; kein Browser-Supabase-Client
[x] RLS ohne Public-Policies (so vorgesehen in schema.sql)
[x] Tokens: randomBytes + SHA-256, nach Confirm gelöscht
[x] Admin-Cookie HttpOnly, SameSite, Secure in Prod, timingSafeEqual
[x] Turnstile Siteverify; Cron hinter CRON_SECRET
[x] .env* in .gitignore
[x] Double-Opt-in + Captcha gegen Spam/Fake

Was er kritisieren würde
------------------------
[ ] Service-Role-Leak = volle DB/PII (Hoch, wenn Key rauskommt)
    → Key nie im Frontend; Rotation; Zugriff dokumentieren

[ ] Ein ADMIN_SECRET für alles; Cookie = Hash(Secret) → Secret kennt Cookie
    → Später zufällige Session (HMAC/JWT), MFA/IdP

[ ] Admin-Login ohne Rate Limit → Online-Guessing
    Datei: app/api/admin/login/route.ts

[ ] Turnstile in Prod abschaltbar bei fehlender Env (Hoch bei Fehlkonfig)

[ ] Schwaches Rate Limit über Serverless-Instanzen (Mittel)

[ ] E-Mail-Enumeration möglich (409 wenn schon confirmed) (Niedrig–Mittel)
    → Einheitliche Antwort „Prüfe dein Postfach“

[ ] Fehlerdetails an Client (Resend-Text / Config-Hinweise) (Niedrig–Mittel)
    Datei: app/api/register/route.ts
    → Generische Meldungen nach außen, Details nur Server-Log

[ ] Confirm per GET (Niedrig–Mittel) – Prefetch/Scanner

[ ] CSV/PII ohne Audit-Log wer exportiert hat (Mittel Betrieb)

[ ] Keine zusätzlichen Security-Headers in next.config.ts (Niedrig–Mittel)

[ ] View registrations_confirmed: Grants in Supabase prüfen
    (Tabelle-RLS allein deckt Views nicht immer ab)

[ ] Admin-Cookie path="/" (Low) → besser path=/admin

Priorität Security
------------------
[x] P0  Production fail-closed (Captcha/Mail/Secrets)
P0  Supabase: anon/authenticated haben KEIN Recht auf Tabelle/View
P0  Secrets rotieren, falls je in Chat/Screenshots (api-keys.txt aus Git entfernt)
[x] P1  Rate-Limit + Lockout auf Admin-Login (5/15 Min.)
[x] P1  Einheitliche Register-Antworten (weniger Enumeration)
P1  Bessere Admin-Session + Audit Login/Export
[x] P1  API-Fehler sanitizen (Register: generische Client-Meldungen)
[x] P2  Security-Headers / CSP (Turnstile allowlist) – POST-Confirm offen
P3  Shared-Secret durch echtes IdP + MFA ersetzen


================================================================================
MVP-STUDIE vs. ENTERPRISE-STANDARD
================================================================================

Bereich          | Jetzt (Studie)              | Enterprise
-----------------+-----------------------------+---------------------------
Auth             | 1 Shared-Secret             | SSO, Rollen, 2FA
Missbrauch       | Turnstile + schwaches RL    | Distributed RL + WAF
Datenbankzugriff | Service Role serverseitig   | Scoped Roles, Rotation
Retention        | nur pending cleanup         | auch confirmed + Holds
DSGVO-Betrieb    | Text + manuell              | DSAR-Workflow, Consent-Ver.
Recht            | Platzhalter                 | Final + AVV
Audit            | keins                       | Login/Export/Löschung
Qualität         | keine Tests                 | Tests, Staging, Monitoring
